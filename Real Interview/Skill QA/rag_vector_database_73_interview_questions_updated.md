### 1. What is RAG (Retrieval-Augmented Generation), and how does its basic pipeline work? (V.Imp)

**Answer:**

RAG stands for Retrieval-Augmented Generation. It is a technique where
we retrieve relevant information from an external knowledge source and
provide it to an LLM before asking it to generate an answer.

The basic pipeline has two phases.

**Document ingestion:** 1. Collect documents such as PDFs, Word files,
and web pages. 2. Extract the text. 3. Split the text into smaller
chunks. 4. Generate embeddings for each chunk. 5. Store the vectors,
text, and metadata in a vector database.

**Query processing:** 1. The user asks a question. 2. Convert the
question into an embedding using the same embedding model. 3. Search the
vector database for relevant chunks. 4. Optionally rerank the retrieved
chunks. 5. Send the question and selected context to the LLM. 6. Return
the generated answer, ideally with source references.

**Example:** Suppose we upload 500 company policy documents. If an
employee asks, "How many sick leaves do I get?", RAG retrieves the
relevant leave-policy section and gives it to the LLM. The LLM then
answers using that company policy.

**Real-world use:** RAG is useful for enterprise chatbots, document
question-answering systems, and assistants that need information from
private or frequently updated sources.

### 2. What is Chunking and Why Is It Necessary for Big Data? (V.Imp)

**Answer:**

Chunking is the process of splitting a large document into smaller
pieces called chunks.

We use it because sending an entire large document to an LLM can exceed
the context window, consume too many tokens, and include information
unrelated to the user's question.

**Example:** Suppose we have a 500-page company handbook. Instead of
sending the complete PDF every time, we split it into smaller chunks.
When someone asks about leave policy, we retrieve only the chunks
related to leave.

**Why is chunking necessary?**

1.  It makes large documents easier to process.
2.  It helps retrieve smaller, relevant sections.
3.  It reduces unnecessary token consumption.
4.  It helps fit context within the LLM's context window.
5.  It allows us to attach metadata and source references to individual
    sections.

**Real-world use:** Chunking allows a chatbot to search thousands of
documents without sending all their content to the LLM for every
question.

### 3. What is a Vector Database and Examples of Vector Data? (V.Imp)

**Answer:**

A vector database is a database designed to store and search numerical
vectors, also called embeddings.

These vectors represent learned features or semantic information from
data such as text, images, audio, or video.

A traditional database commonly searches using exact values or
conditions. A vector database can find items that are similar in meaning
or features.

**Example:** Consider these sentences:

-   "I want to buy a car."
-   "I am planning to purchase a vehicle."

The wording is different, but the meaning is similar. An embedding model
converts both sentences into vectors, and a vector database can find
that they are close to each other.

**Examples of vector data:** - Text embeddings. - Image embeddings. -
Audio embeddings. - Video-frame embeddings. - Product or user-feature
embeddings.

**Popular options:** Qdrant, Pinecone, Weaviate, Milvus, and Chroma.
PostgreSQL with pgvector and Elasticsearch also support vector search.

**Real-world use:** In RAG, we store document embeddings in a vector
database and retrieve relevant chunks when a user asks a question.

### 4. What is Vectorization?

**Answer:**

Vectorization is the process of converting data into numerical vectors
so that machine-learning models can process it.

Computers and neural networks work with numbers. Therefore, text,
images, and other data need to be represented numerically.

For example, an embedding model can convert the sentence "I love machine
learning" into a vector containing hundreds or thousands of numbers.

`"I want to learn Java"` → `[0.12, -0.45, 0.78, ...]`

The actual values are generated by the model.

**Real-world use:** In RAG, we vectorize document chunks and user
questions so that we can compare them and retrieve semantically related
information.

**Remember:** Vectorization is the broader process of converting data
into vectors. Embedding generation is one common way of creating
meaningful vector representations.

### 5. What is Retrieval-Augmented Generation (RAG) and How Have You Implemented It? (V.Imp)

**Answer:**

RAG combines information retrieval with an LLM. Instead of asking the
LLM to answer only from its pre-trained knowledge, we first retrieve
relevant information from an external knowledge base and provide it as
context.

Suppose I am building a chatbot that answers questions from uploaded
company documents.

**Implementation:**

1.  **Document upload:** Users upload PDFs, Word files, or text files.
2.  **Text extraction:** I extract text using suitable document loaders
    or parsing libraries.
3.  **Chunking:** I split the text into smaller, meaningful chunks.
4.  **Embedding generation:** I generate embeddings for each chunk.
5.  **Vector storage:** I store embeddings, original text, and metadata
    in a vector database such as Qdrant.
6.  **Query processing:** When a user asks a question, I generate an
    embedding for the query.
7.  **Similarity search:** I retrieve the most relevant chunks.
8.  **LLM integration:** I pass the question and retrieved context to
    the LLM with instructions to answer from that context.
9.  **Final response:** The LLM generates the answer, and the
    application returns it with source references where available.

**Architecture:**

`Document → Extraction → Chunking → Embeddings → Qdrant`

`User Query → Query Embedding → Retrieval → Context + Query → LLM → Answer`

**Real-world use:** This approach is useful for chatbots that answer
questions from private documents, internal knowledge bases, or company
data.

### 7. What Are the Different Types of Retrieval in Embedding Models? (V.Imp)

**Answer:**

Retrieval means finding documents or chunks that are relevant to a
user's question.

Some common retrieval approaches are:

1.  **Dense retrieval:** Uses embedding vectors to find semantically
    similar content. For example, a query about "buying a vehicle" may
    retrieve a document about "car purchase."
2.  **Sparse retrieval:** Uses keyword-based methods such as BM25 or
    TF-IDF. It is useful for exact names, codes, and technical terms.
3.  **Hybrid retrieval:** Combines dense and sparse retrieval.
4.  **Metadata filtering:** Filters by fields such as department, date,
    document type, or user permissions.
5.  **Multi-query retrieval:** Creates alternative search queries and
    combines their results.
6.  **Parent-child retrieval:** Retrieves a small child chunk but can
    return its larger parent section to preserve context.

**Real-world use:** In an enterprise RAG system, I may use hybrid
retrieval with metadata filters because semantic matching alone can miss
exact policy names, IDs, or technical identifiers.

### 8. What Are the Components of a RAG Pipeline? (V.Imp)

**Answer:**

A RAG pipeline has two main phases: document ingestion and query
processing.

**1. Document Ingestion Phase**

-   **Document loader:** Reads PDFs, Word files, web pages, and other
    sources.
-   **Text extraction:** Extracts text and, where required, tables.
-   **Chunking:** Splits large content into smaller pieces.
-   **Embedding model:** Converts each chunk into a vector.
-   **Vector database:** Stores vectors, text, and metadata.

**2. Query Processing Phase**

-   **User query:** Receives the question.
-   **Query embedding:** Converts the question into a vector.
-   **Retriever:** Searches for relevant chunks.
-   **Reranker (optional):** Reorders chunks by relevance.
-   **Prompt builder:** Combines the question and selected context.
-   **LLM:** Generates the answer.
-   **Response handler:** Returns the answer and source references.

**Complete flow:**

`Documents → Loader → Extraction → Chunking → Embeddings → Vector DB`

`Question → Query Embedding → Retriever → Reranker → Prompt → LLM → Answer`

**Real-world use:** These components work together to build a chatbot
that answers questions using a private or frequently updated knowledge
base.

### 9. What Is the Difference Between Dense Retrieval and Sparse Retrieval? (V.Imp)

**Answer:**

Dense retrieval and sparse retrieval are two common approaches for
searching documents.

**Dense retrieval** converts text into dense numerical vectors using an
embedding model. It finds documents based on semantic similarity. For
example, a search for "How can I purchase a car?" may find a document
containing "vehicle buying process."

**Sparse retrieval** generally uses keyword-based methods such as BM25.
It is useful when exact words, names, or technical terms matter, such as
a product code or error ID.

  Dense Retrieval                  Sparse Retrieval
  -------------------------------- --------------------------------------------
  Uses embedding vectors           Uses keyword or term-based representations
  Focuses on semantic similarity   Focuses on matching important terms
  Can match different wording      Strong for exact terms
  Requires an embedding model      Can use BM25

**Real-world use:** I would use hybrid retrieval when I need both
semantic understanding and exact keyword matching.

### 10. What Is the Difference Between RAG and Agentic RAG? (V.Imp)

**Answer:**

Traditional RAG follows a relatively fixed workflow. It receives a
question, retrieves relevant documents, and sends those documents to an
LLM to generate an answer.

Agentic RAG adds an AI agent that can decide how to retrieve information
and what action to take next.

**Traditional RAG:** 1. User asks a question. 2. System retrieves
relevant chunks. 3. LLM receives the question and chunks. 4. LLM
generates the answer.

**Agentic RAG:** 1. User asks a question. 2. Agent analyzes the request.
3. It decides whether retrieval is needed. 4. It may choose a knowledge
source or search tool. 5. It evaluates the retrieved information. 6. It
may rewrite the query or retrieve again. 7. It combines the results and
generates the answer.

**Example:** If a user asks, "Compare our current leave policy with last
year's policy," an agentic system can decide to search two policy
versions, compare the relevant sections, and generate a comparison.

**Real-world use:** Agentic RAG is useful for complex questions
requiring multiple retrieval steps, sources, or tools.

**Important:** Agentic RAG adds flexibility, but can also increase
latency, token usage, and complexity.

### 11. What Are the Different Chunking Strategies, and When Would You Use Each? [Scenario Based] (V.Imp)

**Answer:**

The chunking strategy depends on the type of document and how users are
expected to search it.

**1. Fixed-size chunking:** Splits text after a fixed number of
characters or tokens. I would use it for simple text where preserving
paragraph boundaries is not critical.

**2. Fixed-size chunking with overlap:** Repeats some text between
neighboring chunks. For example, 500-token chunks with 50-token overlap.
I would use it when information may continue across chunk boundaries.

**3. Recursive chunking:** Tries natural boundaries such as paragraphs
and sentences before splitting smaller sections. It is a good
general-purpose approach.

**4. Sentence-based chunking:** Splits at sentence boundaries. Useful
when sentence meaning should remain intact.

**5. Paragraph-based chunking:** Keeps complete paragraphs together.
Useful for articles and reports.

**6. Semantic chunking:** Groups sentences based on meaning or topic
changes. Useful for documents containing multiple topics.

**7. Structure-based chunking:** Splits according to headings, sections,
tables, or document structure. Useful for policies, manuals, and legal
documents.

**Real-world use:** For a company-policy RAG system, I would prefer
structure-aware or recursive chunking so that a policy section and its
explanation remain together.

### 16. What Types of Models Are Used for Re-Ranking?

**Answer:**

Reranking models evaluate how relevant each retrieved document is to the
user's original query.

**1. Cross-encoder models**

A cross-encoder receives the query and a document together and
calculates a relevance score.

For example: - Query: "What is the refund policy?" - Document A:
Contains the refund policy. - Document B: Contains the office address.

The cross-encoder should score Document A higher. Cross-encoders are
generally accurate for relevance scoring, but more computationally
expensive because each query-document pair must be processed.

**2. Bi-encoder models**

A bi-encoder independently converts the query and document into vectors.
Their similarity can be calculated efficiently. These models are
commonly used for initial dense retrieval.

**Examples:** BGE Reranker models, cross-encoder models from Sentence
Transformers, and Cohere Rerank models.

**Real-world use:** In RAG, I may retrieve 20 candidate chunks using
vector or hybrid search, then use a cross-encoder reranker to select the
best 5.

### 17. How Would You Debug If the RAG System Gives a Wrong Answer? [Scenario Based] (V.Imp)

**Answer:**

If a RAG system gives an incorrect answer, I would not immediately
assume the LLM is the problem. I would debug each stage separately.

1.  **Document ingestion:** Verify that the correct document was
    uploaded and its text was extracted properly.
2.  **Chunking:** Inspect whether important information was split
    incorrectly or separated from its heading.
3.  **Embeddings:** Verify that the same compatible embedding model and
    configuration are used for documents and queries.
4.  **Retrieval:** Log retrieved chunks, scores, document IDs, and
    metadata. Check whether the expected information appears in top-K
    results.
5.  **Reranking:** Check whether the reranker pushes relevant chunks
    down.
6.  **Prompt construction:** Inspect the final prompt to ensure correct
    context and clear instructions.
7.  **Generation:** If context is correct but the answer is wrong,
    investigate the prompt, model output, decoding settings, and
    validation.

**Real-world use:** I would maintain logs and a test dataset containing
questions, expected source documents, and expected answers. This helps
identify whether the issue is ingestion, retrieval, reranking, or
generation.

### 21. How Does Similarity Search Work in Vector Databases? (V.Imp)

**Answer:**

Similarity search finds vectors closest to a given query vector
according to a selected similarity or distance metric.

In RAG, the embedding model converts the user's question into a vector.
The vector database compares this vector with stored document vectors.

**Example:** These sentences have similar meanings: - "I want to
purchase a car." - "I want to buy a vehicle."

Their embeddings may be close to each other.

The database searches for vectors close to the query vector and returns
the associated documents.

**Common measures:**

1.  **Cosine similarity:** Measures the cosine of the angle between two
    vectors.
2.  **Dot product:** Calculates the dot product of two vectors.
3.  **Euclidean distance:** Measures straight-line distance between
    vectors.

The correct metric depends on the embedding model and how its vectors
are intended to be compared.

**Real-world use:** In Qdrant, we configure a distance metric for a
collection and use it to retrieve document vectors similar to the user's
query.

### 25. How Does a Vector Database Retrieve Relevant Embeddings from a Large Dataset? (V.Imp)

**Answer:**

A vector database uses vector indexes and similarity or distance
calculations to find vectors close to the user's query vector.

Suppose we have one million document embeddings.

2.  The vector database receives the query vector.
3.  Its search index helps identify nearby candidate vectors.

vector one by one.

One popular indexing approach is HNSW.

chunks efficiently.

### 26. What Retrieval Algorithms Are Used in Vector Search? (V.Imp)

**Answer:**

Vector search uses different algorithms and indexing techniques to find
vectors similar to a query.

**1. Exact or brute-force search:** Compares the query vector with every
stored vector. It can provide exact results but becomes expensive for
very large datasets.

**2. Approximate Nearest Neighbor (ANN):** Finds very close matches
without checking every vector. It trades a small amount of search
accuracy for improved speed.

**3. HNSW:** Hierarchical Navigable Small World is a graph-based ANN
indexing method. It connects vectors through graph layers so search can
navigate efficiently toward nearby vectors.

**4. IVF:** Inverted File Index divides vectors into clusters and
searches selected clusters rather than the complete dataset.

**5. Product Quantization:** Compresses vectors into smaller
representations to reduce memory usage and speed up search, with some
accuracy trade-offs.

**Real-world use:** For a large RAG collection, I would evaluate the
indexing method based on search latency, recall, memory, and dataset
size.

### 29. Calculate the Teacher's Weight Given Class Average Weights Before and After Inclusion. (V.Imp)

**Answer:**

on the values provided in the question.

Total student weight before including the teacher:

`n × A`

Total weight after including the teacher:

`(n + 1) × B`

Therefore:

`Teacher's Weight = (n + 1) × B − n × A`

**Example:**

`Teacher's Weight = (21 × 52) − (20 × 50)`

`= 1092 − 1000 = 92 kg`

### 31. How Do Embeddings Work? (V.Imp)

**Answer:**

machine-learning model.

For text, an embedding model converts a sentence, paragraph, or document
into a vector containing numerical values. These values represent
learned features and semantic relationships.

**Example:**

-   "I want to purchase a vehicle."

model is designed to produce vectors that are close to each other for
semantically similar text.

On the other hand, "I want to buy a car" and "The weather is cold" are
about different topics, so their embeddings would generally be less
similar.

**How embeddings are used in RAG:**

1.  Extract text from documents.
2.  Split text into chunks.
3.  Generate an embedding for each chunk.
4.  Store embeddings in a vector database.
5.  Generate an embedding for the user's question.
6.  Search for similar vectors.
7.  Retrieve the corresponding text chunks.

**Real-world use:** Embeddings allow RAG to search by meaning instead of
relying only on exact keyword matches.

### 55. What Principle Does Qdrant Use for Vector Similarity Search?

**Answer:**

Qdrant performs vector similarity search using a configured distance
metric and vector index.

It supports metrics such as cosine similarity, dot product, and
Euclidean distance.

For scalable approximate nearest-neighbor search, Qdrant uses the HNSW
indexing approach.

**What is HNSW?**

HNSW stands for Hierarchical Navigable Small World. It is a graph-based
ANN indexing method.

It connects vectors through a hierarchy of graph layers. During search,
the algorithm navigates through these connections to find nearby vectors
without comparing the query against every vector in the collection.

**Example:** If we have one million document embeddings, the HNSW index
helps locate nearby candidates efficiently rather than performing a full
comparison for every query.

### 59. How Would You Implement Hybrid Search Using Dense and Sparse Retrieval? [Scenario Based] (V.Imp)

**Answer:**

Hybrid search combines dense retrieval and sparse retrieval.

Dense retrieval finds information based on semantic similarity, while
sparse retrieval finds information based on keyword matching.

**Example:** A user asks, "How do I fix error code ERR-104 during
login?"

Dense retrieval may find documents about login failures and
authentication problems. Sparse retrieval may find the exact document
containing `ERR-104`.

**Implementation approach:**

1.  Receive the user's query.
2.  Generate a dense query vector using an embedding model.
3.  Run dense vector search.
4.  Run sparse keyword search, for example using BM25.
5.  Combine the result lists.
6.  Use a fusion method such as Reciprocal Rank Fusion (RRF) or
    normalized score combination.
7.  Optionally rerank the combined candidates.
8.  Pass the best chunks to the LLM.

**Flow:**

`User Query → Dense Search + Sparse Search → Result Fusion → Reranking → LLM`

**Real-world use:** Hybrid search is useful in enterprise RAG systems
where users ask natural-language questions but also search for exact
policy names, product codes, and technical identifiers.

### 60. How Would You Build a Hybrid Retriever Combining Dense Embeddings and Sparse Retrieval? [Scenario Based] (V.Imp)

**Answer:**

I would build a hybrid retriever with two independent retrieval paths.

**1. Dense retrieval path:** - Generate embeddings for document
chunks. - Store them in a vector database. - Generate an embedding for
the user's query. - Retrieve semantically similar chunks.

**2. Sparse retrieval path:** - Build a keyword search index using a
method such as BM25. - Search the same document collection using the
user's query terms. - Retrieve chunks with strong keyword matches.

**3. Combine results**

The two result lists can be combined using Reciprocal Rank Fusion (RRF).
RRF combines rankings rather than requiring both search systems to
return scores on the same scale.

A simplified formula is:

`RRF score(d) = Σ 1 / (k + rank(d))`

Here, `rank(d)` is the position of document `d` in each result list, and
`k` is a smoothing constant.

**4. Rerank:** Optionally use a cross-encoder to select the most
relevant chunks.

**5. Generate answer:** Pass the selected context to the LLM.

**Real-world use:** I would use this architecture when semantic meaning
and exact keyword matching are both important.

### 62. What Is the "Lost in the Middle" Phenomenon and How Would You Mitigate It in RAG Architectures? [Scenario Based] (V.Imp)

**Answer:**

The "lost in the middle" phenomenon refers to a behavior observed in
some long-context language models where information near the beginning
or end of a long prompt may be used more effectively than information
placed in the middle.

Even if we provide all relevant information, the model may not use every
part of a very long context equally well.

**Example:** Suppose we retrieve 20 chunks and place them in one long
prompt. The most important chunk may be in the middle, and the LLM might
fail to use it correctly.

**How would I mitigate it?**

1.  **Reduce context size:** Retrieve only the most relevant chunks.
2.  **Use reranking:** Put the strongest evidence first.
3.  **Remove redundancy:** Avoid sending repeated information.
4.  **Use structured context:** Group information by heading or source.
5.  **Position evidence carefully:** Place important evidence near the
    beginning or in a clearly marked section.
6.  **Use contextual compression:** Remove irrelevant sentences.
7.  **Evaluate ordering:** Test different chunk-ordering strategies on
    real questions.

**Real-world use:** In a RAG system with many retrieved documents, I
would optimize both the number and ordering of chunks rather than
assuming a larger context always produces a better answer.

### 63. What Are Common Retrieval and Generation Metrics in AI Systems? (V.Imp)

**Answer:**

    question.

**Performance metrics:** Average latency, p95 latency, throughput, token
consumption, and cost per request.

**Real-world use:** I evaluate retrieval and generation separately
because a good answer depends on both finding the right evidence and
using that evidence correctly.

### 64. Write a Function to Perform Similarity Search on a List of Documents.

**Answer:**

If I have a list of documents with embeddings, I can calculate
similarity between a query vector and each document vector. For a simple
example, I can use cosine similarity.

**Python example:**

``` python
import numpy as np

def cosine_similarity(vec1, vec2):
    vec1 = np.array(vec1)
    vec2 = np.array(vec2)

    denominator = np.linalg.norm(vec1) * np.linalg.norm(vec2)

    if denominator == 0:
        return 0.0

    return float(np.dot(vec1, vec2) / denominator)


def similarity_search(query_vector, documents, top_k=3):
    results = []

    for document in documents:
        score = cosine_similarity(
            query_vector,
            document["embedding"]
        )

        results.append({
            "text": document["text"],
            "score": score
        })

    results.sort(
        key=lambda item: item["score"],
        reverse=True
    )

    return results[:top_k]
```

**Explanation:**

1.  The query vector represents the user's question.
2.  Each document contains its embedding.
3.  We calculate cosine similarity between the query and each document.
4.  We sort results by similarity in descending order.
5.  We return the top-K documents.

**Important:** This is a brute-force implementation. For millions of
documents, I would use a vector database with an appropriate ANN index
instead of comparing every vector in Python.

### 67. What Retrieval Metrics Would You Use to Measure the Accuracy of a RAG System? (V.Imp)

**Answer:**

To measure retrieval accuracy, I would use metrics that tell me whether
the correct documents are retrieved and how highly they are ranked.

**1. Precision@K**

It measures the proportion of retrieved top-K results that are relevant.

For example, if 8 out of 10 retrieved chunks are relevant:

`Precision@10 = 8 / 10 = 0.8`

**2. Recall@K**

It measures the proportion of all relevant documents that appear in the
top-K results.

For example, if there are 10 relevant chunks and the system retrieves 7:

`Recall@K = 7 / 10 = 0.7`

**3. Mean Reciprocal Rank (MRR)**

It measures the position of the first relevant result. A relevant result
at rank 1 gives a higher reciprocal rank than one at rank 5.

**4. NDCG**

It evaluates ranking quality while considering graded relevance and the
position of each result.

**Real-world use:** I would use Recall@K to check whether relevant
information is found, Precision@K to check how much retrieved
information is useful, and MRR or NDCG to evaluate ranking quality.

### 73. What Chunk Size Should Be Used in a RAG Architecture? (V.Imp)
